# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FinancialFFT.jl is a Julia package that prices European options (vanilla, binary, and smile variants) via Fourier/characteristic-function methods. It is an extension of [FinancialMonteCarlo.jl](https://github.com/rcalxrc08/FinancialMonteCarlo.jl): it reuses that package's processes (`BlackScholesProcess`, `MertonProcess`, `KouProcess`, NIG, VarianceGamma, …), `EuropeanOption`, `ZeroRate`, `Underlying`, and adds new `pricer` methods, so the only export is `pricer` plus the method configurator structs.

## Commands

```julia
] test FinancialFFT                      # full suite (what CI runs, Julia 1.11 / 1.12), ~7 minutes
julia --project=. -e 'using Pkg; Pkg.test()'
julia --project=. -e 'using Pkg; Pkg.test(test_args = ["extrema_computation", "multiple_options"])'  # selected suites
julia --project=. -e 'using Pkg; Pkg.test(test_args = ["gpu"])'  # GPU suite, needs a CUDA GPU (not in SUITES, not run by CI)
```

- Tests are organised in suites: `test/runtests.jl` loads the shared `utils.jl` and `cases.jl`, then `include`s `<suite>_test.jl` for every name in its `SUITES` list (or only those passed as `test_args`). A new suite file must be added to `SUITES`; other files in `test/` are not run. The exception is `gpu_test.jl`, kept out of `SUITES` because CI has no GPU; for the same reason CUDA is not a test dependency, and `runtests.jl` adds it to the test environment only when the suite is selected. It runs METHOD_CASES (prices, ForwardDiff, Zygote) in `CudaMode`, with smile strikes as `CuArray`s, and compares other models and smiles with the CPU.
  - `cases.jl` (`METHOD_CASES`) declares, per method, the supported payoffs and the tolerance for each number type / AD back-end; `black_scholes` and `gradients` loop over it against `blsprice`/`blsbin` from FinancialToolbox. `other_models` compares the other methods with `LewisMethod` on Merton, Kou, VG, NIG and Heston (`model_cases`).
  - Known failures are recorded as `Broken(toll)` (see `utils.jl`), which becomes `@test_broken`: the suite reports "Unexpected Pass" as soon as one starts working, so update `cases.jl` when fixing one.
- Formatting: JuliaFormatter with `.JuliaFormatter.toml` (margin=1200, i.e. effectively no line wrapping).
- Docs: `docs/make.jl` (Documenter). It first runs `docs/figures.jl`, which computes the figures with the package and saves each as SVG in a light and a dark variant in `docs/src/assets/figures/` (git-ignored); `assets/figures.css` shows the one of the reader's theme. Plots exports a `density` too: qualify it as `FinancialFFT.density` there. CI also uses a custom registry `rcalxrc08/LocalRegistry` for `FinancialMonteCarlo`; resolve it when setting up a fresh environment.

## Architecture

Entry point [src/FinancialFFT.jl](src/FinancialFFT.jl) includes, in order: `abstracts`, `mods` (every scalar `_mod` hook), `extrema_computation_opt` (the Chernoff range, `compute_chernorff_limits`), `utils` (shared utilities: grids and types, FFT, Clenshaw, payoff conversions), `charexp`, then the methods (`carrmadan`, `carrmadan_lewis`, `lewis`, `cos`), and the densities: `density` (the interface only), `utils_density` (shared by the densities and their pricers), `cos_density`, `fft_density`.

**Densities** ([src/methods/density.jl](src/methods/density.jl), the interface only): `density(process, zero_rate, method, T[, mode])` is the interface, like `pricer`, for callers that need a density without a closed formula (Vibrato, likelihood ratio method): it returns an `AbstractDensity` of the log-return `log(S_T / S_0)`, independent of `S_0`, zero outside `[a, b]`. The interface defines `f(y)` (a number, on the CPU) and `density_values(f, y)` (an array) for every density, from two functions a density type implements without the mask: `density_value(f, y)` at a number and `density_array(f, y[, mode])` at an array (default: `density_value` at each point; the mode lets a pricer pick the CPU kernel). `mask_outside_range` (in `utils_density.jl`) zeroes them outside the range. A method that computes a density subtypes `AbstractDensityMethod` and adds a `density` method; with an `M` field it also prices through the one `pricer` of `utils_density.jl`, `density_integral_price`: Simpson's rule for the put on a log-moneyness grid ending at the strike (constant for differentiation: `ignore_derivatives_mod`), call by parity; a smile shares the density, so its prices are the ones of the single options. `CosDensityMethod(N, M)` ([src/methods/cos_density.jl](src/methods/cos_density.jl)) gives a `CosDensity` on the range of COS: `density_value` is a Clenshaw recurrence (`clenshaw_cos_sum`), `density_array` broadcasts and a reduction only, with the coefficients as broadcast arguments (GPU), and in `SerialMode` the recurrence per node (`map`). `FFTDensityInverter(N, M)` ([src/methods/fft_density.jl](src/methods/fft_density.jl); `DensityInverter`, which priced with a density in log-moneyness and needed `xmax`, was removed in its favour) gives an `FFTDensity`: one FFT (`fft_density_values`) on the Chernoff range of COS, shifted to its centre, and cubic Lagrange interpolation on four nodes (`lagrange_cubic`), with gathers instead of a spline, so that Zygote differentiates it (Interpolations' spline construction mutates arrays) and it runs on the device; the range goes through `ignore_derivatives_mod`, a zero-derivative primitive in the Mooncake extension (Mooncake ignores `@ignore_derivatives`, and a grid moving with the parameters adds the derivative of the interpolation error to the scores). It replaces the FFT density of VibratoMonteCarlo.jl (`lrm_aug.jl`), to be removed there after the next release (VibratoMonteCarlo issue #37 says how). The untracked `density_cos.jl` is the original sketch. Order matters (later files use earlier definitions).

**Dispatch design.** Each method is a configurator struct subtyping `FinancialMonteCarlo.AbstractMethod` via `AbstractFFTMethod` (Carr-Madan, Carr-Madan-Lewis; use `fft`) or `AbstractIntegralMethod` (Lewis, COS; direct quadrature/cosine sums), `AbstractDensityMethod <: AbstractIntegralMethod` for the density methods. Pricing is invoked as `pricer(process, zero_rate, method, payoff[, mode])`, extending `FinancialMonteCarlo.pricer`. Every method has one `pricer` for options and smiles (`FourierPayoff`): several strikes are priced through smiles, options with different maturities by broadcasting `pricer.`, and there is no `pricer` taking a vector of strikes or an array of options.

**Characteristic exponents** ([src/methods/charexp.jl](src/methods/charexp.jl)): per-process `characteristic_exponent_i(imv, process)` (scalar) and `characteristic_exponent_vi` (broadcast), implemented as real functions of an imaginary-argument input (`ψ(v) = ψ_i(v*im)`) to avoid complex arithmetic. A new process needs these methods. Methods call the three-argument `characteristic_exponent_i(imv, process, T)`, the log of `E[exp(imv X_T)]`, which defaults to `ψ_i * T`: a process that is not Lévy (Heston, nonlinear in `T`) defines the three-argument `_i`/`_vi` instead. `charexp_and_ders.jl` (untracked) is WIP for derivatives.

**Carr-Madan** ([src/methods/carrmadan.jl](src/methods/carrmadan.jl)): damped call transform, without intrinsic value: the undamped time value has a kink at the forward and decays like `1/v²`. The damping `α` is capped by `exponential_moment_bound`, and `A / 2^Npow` must be small with respect to it. The binary call is minus the strike derivative of the call: `α + iv` leaves the denominator, and the price is divided by `K`.

**Payoff handling** ([src/methods/utils.jl](src/methods/utils.jl), `smile.jl`): everything but COS and the density pricers is priced as a call and converted with `call_to_put` (dispatching on vanilla/binary/smile option types). COS and the density pricers expand the put and convert it with `put_to_option`: the coefficients of a call grow like `exp(b)`, so a call needs the right tail under the share measure, which the range does not cover and widening it would only trade for rounding errors. The binary call is minus the strike derivative of the Lewis formula: Carr-Madan-Lewis shares one kernel, with `lewis_denominator` and `carr_madan_lewis_call` selecting the payoff,. The `fft` overloads of the AD back-ends take vectors: every FFT is of a vector.

**Truncation range of the COS method** ([src/methods/extrema_computation_opt.jl](src/methods/extrema_computation_opt.jl)): `[a, b]` comes from a Chernoff bound on the tails of the log-price, `t(s) = (T ψ_i(mul s) - log ε) / s` minimised over `s` by bisection on its (complex-step) derivative; `mul = 1` is the upper tail, so the endpoint is `driftT + mul t`, and only skewed models tell the two sides apart. The complex step is `eps(s)`, except for Heston (`sqrt(eps(s))`), whose imaginary parts cancel when `γ` is imaginary. The search bracket starts at `[1, 50]` and is doubled for short maturities (the optimum grows like `1/√T`), but never beyond `exponential_moment_bound(process, mul[, T])`, where `E[exp(mul s X)]` stops being finite (Kou `λ₊`/`λ₋`, VG/NIG from the log/sqrt argument, Heston from the moment explosion time, hence the `T`; `Inf` otherwise): past it `characteristic_exponent_i` returns meaningless finite values. A new process with semi-heavy tails needs an `exponential_moment_bound` method. The range is for `log(S_T / S0)`: on `y = log(S_T / K)` it moves by `log(S0 / K)`, a constant for AD, and a smile uses the union of the ranges of its strikes. Sharing it shares the payoff coefficients and the phases of the characteristic function, so a strike costs only the series, against 3.5-4.5 times as much with a range per strike; a smile that is wide with respect to the standard deviation needs a larger `N`. The series (`cos_phased_series`) folds the strike-independent phases into complex coefficients once and, in `SerialMode`, sums them per strike with a Clenshaw recurrence (`cos_clenshaw`, evaluated with `map` for ReverseDiff): one `sincos` per strike instead of one `cos` per term and strike, 5-9 times faster for smiles of 100-500 strikes, no gain on a single option, where the characteristic exponent dominates. Other modes (GPU) keep the N×K broadcast `cos(u x + phase)`: the recurrence is sequential in `k` and indexes the coefficients element-wise.

**Clenshaw recurrence** ([src/methods/utils.jl](src/methods/utils.jl)): `clenshaw_exp_sum` (complex coefficients as real/imaginary arrays, `Val(true)` for the real part only) and `clenshaw_cos_sum` (real coefficients) are shared by COS, Lewis smiles and `CosDensity` (its `density_value`, and its `density_array` in `SerialMode`). Near θ = 0 or π (`|cos θ| > 0.95`) they switch to Reinsch's form, on `d_k = b_k - σ b_{k+1}`: about 1.8 times slower per term (longer dependency chain), but on the Lewis coefficients, where `θ = h c` is close to 0 at the money, the plain recurrence errs by up to 1e-7 and Reinsch's by 1e-13. Lewis evaluates the exponent on the nodes `v >= 0` only (the integrand is even: `ψ(1/2 - iv) = conj ψ(1/2 + iv)`), with weight 2, 1 for the node 0 of an odd `N` (`LewisMethodResult.weights`), and uses the recurrence for smiles only (`lw_integrate` with the mode; a single option keeps the broadcast, as cheap), with the nodes `v_j = v_0 + j h` and coefficients from `lewis_coefficients`; smiles return vectors in every mode.

**Execution modes / optional backends.** `FinancialMonteCarlo.BaseMode` (`SerialMode`, `AbstractCudaMode`) is the trailing `pricer` arg. Optional packages are package extensions (`[weakdeps]`/`[extensions]` in `Project.toml`, code in [ext/](ext/)): CUDA (the `adapt_array`/`adapt_itp` hooks, identity by default: grids become `CuArray`s keeping their element type, splines move to the device only when the strikes are there; Interpolations cannot build a spline from device data, so Carr-Madan-Lewis builds it on the host. Needs FinancialMonteCarlo ≥ 0.5.1, which defines `AbstractCudaMode` outside its Requires code; `CarrMadanMethod` ignores the mode and runs on the CPU), DualNumbers, HyperDualNumbers, ForwardDiff, TaylorSeries (these supply `fft` overloads and `real_mod`/`imag_mod`/`v_value_mod` hooks so AD works through FFT and the range computation; TaylorSeries covers `Taylor1` and `TaylorN`, for which Base has no `cis` and whose `abs` refuses a constant term of zero, hence `cis_mod`/`abs_mod`; DualNumbers and HyperDualNumbers have no `sincos`, hence `sincos_mod`, overloaded as `(sin(x), cos(x))` in their extensions; and whose element type says neither the order nor the `JetSpace`, so build constants from a value, with `zero(x)`, not from a type), Mooncake (0.5; `fft` declared as a primitive with `frule!!`/`rrule!!`, since Mooncake cannot differentiate the FFTW plan). Mooncake also fails on type-unstable code with small `Union` return types (e.g. `Union{Float16, Float64}`), so keep pricing paths type stable, and it cannot differentiate the complex `sqrt` of Base (it bitcasts): use the `sqrt_mod` hook, overlaid in the extension. On the GPU, Zygote cannot differentiate broadcasts whose intermediate results are tuples (pass real and imaginary parts as separate arrays), ReverseDiff cannot store tracked reals in GPU arrays, Mooncake's CUDA broadcast rules reject arrays mixing real and complex element types (every kernel but the binary Lewis integrand), and kernels must not index arrays element-wise (`CUDA.allowscalar(false)`; the rrule of `sum` of PatternVectors gives any vector a host `PatternVector` cotangent, and ChainRules then computes `dot(Ȳ, B)` with a device `B`: PatternVectors ≥ 0.1.6 does that `dot` with broadcasts (0.1.7 without ambiguities with ReverseDiff)): the ForwardDiff `fft!` uses only broadcasts and one batched `fft!` with the components along a new last dimension (nested duals of a Hessian recurse into it, one dimension per level). The core code calls hooks like `real_mod`, `imag_mod` (all the scalar ones in [src/methods/mods.jl](src/methods/mods.jl)), `adapt_array` instead of `real`/`imag`/arrays directly; use them when editing numeric kernels. `ChainRulesCore.@ignore_derivatives` is used around non-differentiable setup (pattern vectors, asserts) for Zygote support. ReverseDiff (extension: `fft` recorded as one tape instruction with `bfft` pullback, `v_value_mod`/`ignore_derivatives_mod` for tracked reals) needs ReverseDiff ≥ 1.18 (1.17 overflows the stack materializing complex broadcasts of tracked values) (compat `1.18`), and PatternVectors ≥ 0.1.4, whose ReverseDiff extension resolves the broadcast style conflict with `TrackedStyle` (the compat is 0.1.7, for `dot` on the GPU). ReverseDiff ignores `@ignore_derivatives`: wrap quantities that must stay constants (truncation ranges, grid bounds) in `ignore_derivatives_mod`, or they become tracked and break integer conversions. For the same reason the Carr-Madan-Lewis spline has tracked coefficients: it is evaluated with `map`, since ReverseDiff cannot broadcast a function that captures tracked values.

**Floating-point types** ([src/methods/utils.jl](src/methods/utils.jl), suite `types`): prices keep the float type of the inputs. `float_type(x...)` (the type of `v_value_mod` of their sum) is the type of grids and ranges, and `to_float_type(FT, x)` converts method parameters (`A`, `α`) to it; avoid Float64 literals and `pi * N` (an irrational times an integer is a Float64) in setup code. The Chernoff range uses `scaled_tolerance(FT, 1e-14)` and a bisection tolerance of at least `8 eps(FT)`. FFTW handles Float32/Float64 only: the FFT methods call `fft_mod`, which falls back on `generic_fft` (radix-2, twiddles in the input precision) for other floats; AD element types still reach the `fft` overloads of the extensions.

## Working-tree caveats

The working tree contains many untracked scratch files (`* copy.jl`, `* - Copia.jl`, `*_old.jl`, `zygote_mwe.jl`, `pluto/`, `runner_cuda.jl`). Only files `include`d in `src/FinancialFFT.jl` are live code; do not edit the copies. Note `cosc.jl`, `density_cos.jl`, `extrema_computation.jl` are also not included by the module.
